OPS-2201 — MODEL CORRECTION after Step B missed its predicted range
===============================================================================

PREDICTED Step B: 65-75 req/s   MEASURED: 51.13 req/s   -> prediction MISSED (too high)

JS main-thread cost per request (1 core / throughput):
  before projection: 1/34.09 = 29.33 ms
  after  projection: 1/51.13 = 19.56 ms
  cost reduction: 33.3%
  BYTES reduction: 57.3%

WHY THE PREDICTION WAS WRONG:
  I assumed serialization cost scales with BYTES alone. If it did, a
  57.3% byte reduction would give 2.34x throughput = 80 req/s.
  Actual gain was only 1.50x. So cost is NOT purely bytes-driven.

CORRECTED MODEL — two components, bytes AND rows:
  solving  js_cost = a*bytes + b*rows  on the two measured points:
    a = 4.692 ns/byte      (serialization / socket write)
    b = 1.227 us/row      (mysql2 row-object materialization, does NOT
                                 shrink when you drop a column)
  check: before = 17.06 + 12.27 = 29.33 ms (measured 29.33)
         after  = 7.29 + 12.27 = 19.56 ms (measured 19.56)

  Per-row cost is now 63% of the remaining budget. Dropping columns
  cannot touch it -- only dropping ROWS can. That is exactly what Step C does.

STEP C PREDICTION, from the corrected model (LIMIT 50):
  payload: 50 rows x 155.3 B = ~7764 B (7.6 KiB)
  JS cost: 0.0364 + 0.0614 = 0.098 ms/req
  event-loop ceiling: 1/0.098ms = 10226 req/s

  That ceiling is FAR above anything else in the system, so I predict the
  binding constraint LEAVES the event loop at Step C. Next candidates:
    - connection pool:  2 / W_db. W_db post-index measured 8.1 ms for 10,000
      rows; with LIMIT 50 it should fall a lot, but it is MEASURED not guessed.
    - the host itself: k6 + 5 containers share this laptop's CPUs.
  PREDICTED Step C throughput: several hundred req/s, bounded by pool or host,
  NOT by payload. If it lands near ~10226 the event loop still binds and I am wrong again.
